## In gewone taal

Vandaag controleert de database alleen "bij welk bedrijf hoor je?". Of je
iets **mag** (de vinkjes van je rol), controleert alleen onze eigen server.
Maar de database is ook rechtstreeks bereikbaar: de sleutel daarvoor staat
openbaar in de website, en wie inlogt heeft zijn eigen toegangsbewijs.
Wie dat weet, kan binnen zijn eigen bedrijf langs onze server heen:
artikelen aanmaken zonder recht, voorraadregels wissen, het logboek
aanpassen, of een stuklijstwijziging doorvoeren zonder goedkeuring.

Dit voorstel kiest hoe we dat dichtzetten. Aanbevolen: de database mag
voortaan alleen nog **lezen** wat je rol toelaat, en alles wat iets
**verandert** gaat via vaste databasefuncties die zelf je rechten
controleren. Gewone gebruikers kunnen dan niets meer rechtstreeks
wijzigen.

## Context

Found 2026-10-19 while fixing `STORY-074` (the `current_stock` view leak):

- **Grants** (`20260716000000_initial.sql`): `anon` and `authenticated`
  have `select, insert, update, delete` on **all** public tables and
  `execute` on **all** public functions.
- **RLS policies** are all `FOR ALL … using (tenant_id =
  current_tenant_id())`: tenant-only, no per-command split, no permission
  check.
- **Permissions** (`roles.permissions`, snapshotted into
  `app_metadata`) are enforced only by Hono's `requirePermission`.
- **No function is `security definer`**, so RPCs run as the caller and
  rely on the caller's table rights — which is why those rights are broad.

Consequences, for any logged-in user, via `/rest/v1/…` with their own JWT
and the public anon key (all within their **own** tenant; cross-tenant
access stays blocked by RLS):

1. Write any business table regardless of role (`items`, `bom_lines`,
   `production_orders`, `proposals`, …).
2. `UPDATE`/`DELETE` `stock_ledger` rows — breaks Security Rule 3
   (append-only).
3. `UPDATE`/`DELETE`/`INSERT` `audit_logs` — the audit trail can be
   rewritten or faked (Security Rule 8).
4. Change their own `profiles.role_id`, edit `roles.permissions` rows, or
   rewrite `workflow_steps` — `review_proposal` trusts `profiles.role_id`,
   so a user can make themselves the approver for any step.
5. Call `apply_bom_change_payload` directly — apply a BOM change with no
   proposal or approval at all.
6. Pass any `p_user_id` to RPCs (`complete_production_order`, …) — ledger
   rows attributed to a colleague.

Today the only tenant is the owner's own company with trusted users, so
real risk is low. Before any SaaS customer it is a blocker
(`roadmap` phase "before SaaS customers", next to `STORY-030`/`ADR-003`).

## Options

- **(a) Permission-aware RLS.** Split every policy per command and add
  `has_permission('items.create')` (reading `auth.jwt() -> app_metadata
  -> permissions`) to `insert`/`update`/`delete` policies. Keep writes
  through the user-scoped client as today.
  - + Smallest code change; matches Security Rule 2 ("RLS is the
    enforcement layer").
  - − Permissions come from the JWT, so they lag up to ~1h after a role
    change until `ADR-003` lands. Multi-step RPCs still need the caller to
    hold raw table rights (e.g. `stock_ledger` insert), so rules 2/3 can
    only be partly closed. Many policies to keep in sync with Hono checks.
- **(b) Read-only tables, writes only through `security definer` RPCs.**
  Revoke `insert/update/delete` on all tables from `anon`/`authenticated`;
  keep `select` (tenant RLS, plus view permissions). Every mutation
  becomes an RPC that checks permissions **from Postgres** (`profiles` →
  `roles.permissions`, not the JWT), derives `user_id`/`tenant_id` from
  `auth.uid()` instead of parameters, and pins `search_path`.
  Internal-only functions (`apply_bom_change_payload`, `log_audit_event`,
  `lock_stock_keys`, `provision_tenant`) get `execute` revoked from
  `anon`/`authenticated`.
  - + Closes all six points, including append-only ledger/audit, and
    fixes the stale-JWT gap for writes. One place per action.
  - − Larger: every Hono write (items, BOM lines, roles, users' profile
    rows, proposals create, production create/start/cancel, stock adjust)
    moves into an RPC. Integration tests needed per RPC.
- **(c) Server uses the service key behind Hono checks.** Rejected:
  violates Security Rule 1 and removes RLS as the safety net.

## Recommendation

**(b)**, in two steps so value lands early:

1. *Quick lock-down (≈2 pts):* revoke all table and function rights from
   `anon` (it needs none — login goes to GoTrue directly); revoke
   `update/delete` on `stock_ledger`, `audit_logs`, `proposal_reviews` and
   all writes on `audit_logs`, `profiles`, `roles`, `workflow_steps`,
   `tenants` from `authenticated` where the server already uses the admin
   client or a trigger/RPC for them; revoke `execute` on internal-only
   functions; make `log_audit_event` `security definer`. Verify each with
   a direct-PostgREST integration test like `STORY-074`'s.
2. *RPC migration (≈3–5 pts):* move the remaining writes into
   permission-checking `security definer` RPCs, then revoke the last table
   write rights.

Security Rule 2/4/7 in `CLAUDE.md` get updated to say the database checks
permissions too, with Postgres (not the JWT) as the source for writes.
