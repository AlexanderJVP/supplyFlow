## Context

Discussion of event logging (`stock_ledger`, `audit_logs`) surfaced a
real gap: the current schema tracks stock at a single, tenant-wide
granularity — there is no concept of a warehouse (building/site) or a
location (bin/zone) within one, and no `location_id` anywhere in
`stock_ledger` or `items`. Events like "stock moved" or "order picked"
can't be modeled meaningfully without knowing *where* stock physically
is.

This directly intersects with the product's stated identity in
`CLAUDE.md`: **"This is not a warehouse system. It is a Manufacturing
Operations Platform."** The question was put to the product owner
explicitly rather than assumed: is multi-location/fulfillment a genuine
requirement, or should event logging stay scoped to enriching the
existing single-location stock events (`moved`/`counted` as ledger
reasons, no schema change)?

Answer (2026-08-01): multi-location is a real, confirmed requirement — a
tenant's warehouse can span multiple buildings, each with multiple
locations within it. This is deliberate scope expansion, not scope creep
to be pushed back on.

## Beslissing

- Add a `warehouses` table (tenant-scoped: one row per building/site) and
  a `locations` table (bins/zones within a warehouse, FK to
  `warehouse_id`), both RLS-isolated per tenant like every other table.
  `locations` has a `type` (`location_type` enum: `storage`, `staging`)
  — needed so "available stock" isn't reported as including stock a
  fulfillment order has already picked but not yet shipped.
- **Every `warehouse` is guaranteed exactly one companion `staging`
  location, created in the same transaction as the warehouse itself**
  (`STORY-036`) — same "guarantee the row exists, don't leave it as a
  special case" principle applied to warehouses that this ADR already
  applies to tenants below. Fulfillment's `picked` step always has a
  well-defined destination, never an ad hoc or caller-chosen "a staging
  location".
- **Every tenant always has at least one real `warehouse` + `location`
  row — `NULL` is a temporary rollout state, never a permanent
  convention.** `provision_tenant` creates a default warehouse +
  location for every new tenant, in the same atomic transaction as the
  rest of provisioning (`STORY-041`). Existing tenants are backfilled
  with a default warehouse + location, and all their historical
  `stock_ledger` rows are updated from `location_id IS NULL` to that
  default location (`STORY-042`). Single-location tenants are simply
  multi-location tenants with cardinality 1 — not a separate code path.
  - **Explicit, one-time exception to Non-Negotiable Rule 3 (added
    2026-09-26):** `STORY-042`'s backfill is the *only* sanctioned
    `UPDATE` on existing `stock_ledger` rows. It is allowed because it
    fills in a previously-unknown attribute (`location_id`) without
    touching any quantity, reason, actor, or timestamp — the ledger's
    history of *what happened* is unchanged. It runs only as a reviewed
    migration (never from application code or an RPC), with before/after
    row counts and a `SUM(quantity_delta)` per item/tenant checked equal,
    and Rule 3 stays absolute for everything else.
- `stock_ledger.location_id` is nullable **only during the rollout
  window** (`STORY-037`, so existing code paths keep working while the
  feature lands incrementally) and becomes `NOT NULL` once `STORY-042`'s
  backfill is verified. No feature or query written against this column
  should be designed around `location_id IS NULL` as a permanent
  possibility.
- Extend `ledger_reason` with `moved` and `counted`.
- Stock moves between locations go through a new `move_stock` RPC — one
  atomic transaction writing a negative ledger row at the source location
  and a positive one at the destination, reason `moved`. Never a raw
  location field update.
- **`move_stock` must take an explicit concurrency guard, not inherit
  one implicitly.** A per-location stock balance is a derived `SUM` over
  `stock_ledger`, so there's no physical row for a plain `FOR UPDATE` to
  lock the way `complete_production_order` locks its `production_orders`
  row. `move_stock` takes `pg_advisory_xact_lock` keyed on `(tenant_id,
  item_id, location_id)` for both source and destination — full details
  (key hashing into a `bigint`, deadlock-safe sort order defined on the
  full composite key rather than `location_id` alone so batch moves
  don't silently regress it later, the fact that this is the first use
  of the advisory-lock pattern in this codebase, and that it only
  guards `move_stock`-vs-`move_stock`, not direct table writes that
  already shouldn't happen per Rules 3/4) are specified in `STORY-038`
  so the implementation doesn't have to improvise any of it.
- Introduce a separate **fulfillment order** entity (picked → packed →
  shipped) distinct from `production_orders`, with its own
  `fulfillment_order_lines` (item_id, quantity — same shape as
  `bom_lines`) since an order covers multiple items. Production orders
  *build* things and consume BOM components; fulfillment orders *ship*
  stock that already exists. These are different lifecycles and
  shouldn't be overloaded onto one table.
- **Fulfillment lifecycle → `stock_ledger` mapping is fully specified,
  no new `ledger_reason` values needed:**
  - `picked`: a location transfer, not a new concept — calls the same
    `move_stock` RPC (source location → the source location's
    warehouse's guaranteed `staging` location), reason `moved`,
    `reference_type='fulfillment_order'`.
  - `packed`: a pure status transition on the fulfillment order (box
    count, tracking info). No physical stock movement, so **no ledger
    entry**.
  - `shipped`: the point stock actually leaves the tenant. Writes a
    negative `stock_ledger` row using the reason that already exists in
    the base schema (`shipped` — see `CLAUDE.md`'s `ledger_reason` enum),
    at the staging/shipping location, `reference_type='fulfillment_order'`.
- **Indexing is decided now, not left to implementation time**: an
  explicit composite index on `stock_ledger (tenant_id, item_id,
  location_id)` (`STORY-037`) — needed by the location-scoped
  `current_stock` variant, `move_stock`'s balance checks, and the
  fulfillment ledger writes above; `locations` gets a
  `unique(warehouse_id, name)` constraint and `fulfillment_order_lines` a
  `unique(fulfillment_order_id, item_id)` constraint, both doubling as
  their own lookup index the same way existing tables already get
  indexing for free from unique constraints rather than bare
  `CREATE INDEX` statements.
- `CLAUDE.md`'s opening product framing gets an inline caveat now (done
  as part of this revision, not deferred) noting the confirmed-but-
  unshipped scope expansion, so the doc doesn't silently contradict a
  decision that's already been made; the full rewrite of that framing
  still waits for `EPIC-009` to actually ship (`STORY-040`).

## Redenen

- A single tenant-wide stock number can't represent "which building, which
  bin" — this is a structural gap, not something a bigger enum or a JSON
  field could reasonably paper over.
- Keeping fulfillment orders as their own entity, rather than extending
  `production_orders` with pick/pack/ship statuses, avoids retrofitting
  risk onto the existing, tested production-order/BOM-consumption flow
  (`complete_production_order`, `can_produce`) — those stay untouched.
- A temporarily-nullable `location_id` keeps the rollout additive:
  existing `stock_ledger` rows and in-flight code don't break the moment
  the column is added; location-awareness rolls out incrementally
  (`STORY-037` → `STORY-038` → `STORY-039`).
- **Sentinel warehouse/location rows (not a permanent `NULL`
  convention) were chosen deliberately, for a product meant to run for
  real companies over years, not just to ship this epic:**
  - SME tenants (10–250 employees) are predominantly single-location.
    If `NULL` stayed the permanent representation of "default location",
    the *most-used* code path in production would be the
    *least-exercised* one in development, since multi-location features
    get built and tested against the tenants that actually have multiple
    locations.
  - `NULL` can't carry a name, address, or capacity. A real row can — and
    that's needed the moment any report, export, or invoice needs to show
    "which location" for a single-location tenant too.
  - A real row lets `location_id` eventually become `NOT NULL` with a
    normal FK. Permanent `NULL` would mean every future join,
    aggregation, and RLS policy needs `COALESCE`/`IS NULL` special-casing
    forever — a standing tax with no point at which it's "done".
  - This mirrors why `bom_lines`/`items` don't special-case "no BOM" as
    `NULL` scattered through queries — the absence of children is just an
    empty result set, not a sentinel value every consumer must know about.
- The fulfillment lifecycle's ledger mapping reuses `moved` (already
  being added for `move_stock`) and `shipped` (already in the base
  `ledger_reason` enum) instead of inventing new reasons — fewer enum
  values to keep in sync between the DB, `packages/shared`, and any UI
  that renders ledger reasons.
- `move_stock` as an RPC (not a direct row update) follows the same
  append-only-ledger + atomic-RPC conventions already established by
  Non-Negotiable Rules 3 and 4, instead of inventing a new mutation
  pattern for this one feature.
- `pg_advisory_xact_lock` over `SERIALIZABLE` isolation for `move_stock`'s
  concurrency guard: it's transaction-scoped (auto-released on
  commit/rollback), needs no schema change, and doesn't require every
  caller to add serialization-failure retry logic — a smaller, more
  contained change than switching this RPC's isolation level.
- A `staging` location type (not an untyped "somewhere in between" row)
  is necessary, not optional, once fulfillment writes to `stock_ledger`:
  without it, picked-but-unshipped stock is indistinguishable from
  ordinary available stock in every location-scoped query, and could be
  double-allocated to a second order or a production run. Guaranteeing
  one `staging` location per warehouse by construction (created with the
  warehouse, not looked up or created ad hoc by the `picked` step) keeps
  `STORY-039` from having to special-case "what if this warehouse has no
  staging location yet".
- An inline CLAUDE.md caveat now, instead of waiting for `STORY-040`'s
  full rewrite: `STORY-040` tracks the *process* of eventually rewriting
  the framing once the feature ships, but doesn't by itself stop the doc
  from asserting something already known to be superseded in the
  meantime. A one-line, clearly time-boxed note closes that window at
  near-zero cost, without pre-writing the future-state description
  before the feature exists.

## Consequenties

- This is a genuine, deliberate scope expansion of the product's
  identity, not just a logging enhancement — `CLAUDE.md`'s "this is not a
  warehouse system" line already carries an inline caveat pointing at
  this ADR (added as part of this revision), and gets fully rewritten
  once `EPIC-009` ships (`STORY-040`) so the source-of-truth doc doesn't
  contradict shipped functionality.
- Existing tenant-wide features (`inventory/alerts`, CSV export,
  `can_produce`, `complete_production_order`) will eventually want
  location-awareness too. During the rollout window they keep working
  unchanged against the tenant-wide `current_stock` rollup; once every
  tenant has a guaranteed default location (`STORY-041`/`STORY-042`)
  these can adopt location scoping without a `NULL` special case to
  design around.
- `complete_production_order` will need to write its `produced` ledger
  entry to a location too, once this lands — defaults to the producing
  tenant's default location unless the production order specifies
  another. Falls out naturally from every tenant always having a default
  location; not a separate design decision.
- Two new provisioning/migration stories added as a direct result of this
  review (`STORY-041`: default warehouse+location on `provision_tenant`;
  `STORY-042`: backfill existing tenants and drop `stock_ledger
  .location_id`'s nullability) — these close the "what happens to new
  vs. existing tenants" gap that the original draft of this ADR left
  implicit.
- `fulfillment_order_lines` (item_id, quantity per line) is now part of
  `STORY-039`'s scope — a fulfillment order covering multiple items is
  not representable without line items, and the ledger-per-item mapping
  depends on them existing.
- Meaningfully larger schema/RLS surface than a typical single-feature
  change (two new tables for locations, a new FK, two new RPCs
  (`move_stock`, plus reusing existing RPC conventions for fulfillment
  transitions), a new order entity with its own line-item table) —
  staged as its own epic rather than a single story.
- **Pre-existing gap surfaced by this review, not caused by it and not
  fixed here**: `complete_production_order`'s `FOR UPDATE` locks only
  the `production_orders` row, not the component items' derived stock —
  two concurrent production orders consuming the same component could
  both read sufficient stock and jointly overdraw it negative. This
  predates `ADR-002` and is out of this epic's scope (production orders
  are untouched by this ADR), but it means `ADR-001`'s planned
  `reserve_stock`/`release_reservation` — which cites
  `complete_production_order`'s locking as the pattern to follow — would
  inherit the same gap unless it's designed with an explicit guard (e.g.
  the same advisory-lock approach) instead of copying the existing
  pattern as-is. Flagged here since it was found while reviewing
  `move_stock`'s concurrency; not resolved as part of this ADR.
- **Pre-existing observation, also not fixed here**: `stock_ledger` has
  no index at all today, not even on `(tenant_id, item_id)` for the
  existing tenant-wide `current_stock` view — every query against it is
  currently a sequential scan. `STORY-037`'s new composite index is
  scoped to what this epic's own query patterns need; it doesn't retrofit
  the existing tenant-wide path. Worth a dedicated look as `stock_ledger`
  grows (this epic itself adds two new write paths — `move_stock` and
  fulfillment — on top of existing growth), but that's a separate
  decision from this ADR.
- Interacts with the stock-reservation RPC proposed in `ADR-001`
  (`EPIC-008`/`STORY-035`): a fulfillment order's `picked` step claims
  stock without a reservation until `ADR-001` lands, which means two
  fulfillment orders could pick the same stock concurrently. Not a
  blocker for either ADR, but tracked as an explicit known follow-on
  dependency in `STORY-039` rather than left only in this ADR's
  Consequenties, since it's the correctness-relevant one.
- Explicitly **not MVP** — deferred to a later sprint per product
  decision (2026-08-01); the accompanying epic/stories are staged as
  `backlog`.
