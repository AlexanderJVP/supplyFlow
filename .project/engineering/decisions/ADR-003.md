## In gewone taal

Rechten van een gebruiker zitten "ingebakken" in zijn inlogbewijs (een
token). Als een beheerder iemands rechten intrekt, blijft dat oude bewijs
tot een uur geldig. Dit voorstel geeft elk profiel een versienummer: bij
elke rechtenwijziging gaat het omhoog, en de server weigert bewijzen met
een oud nummer. De database is daarbij altijd de baas; het inlogbewijs is
enkel een kopie die zichzelf herstelt als ze niet meer klopt.

## Context

Permissions are baked into a user's JWT `app_metadata` at invite/role-
assignment time (Non-Negotiable Security Rule 7), so `requirePermission`
never needs a database lookup. The known gap (`STORY-030`, `EPIC-001`):
when a user is demoted or their role's permissions are edited,
`roles.ts`/`users.ts` update the DB and re-push `app_metadata`, but a JWT
the user already holds keeps its old permissions until it expires (~1h).

Three options were considered: a version check in `requireAuth`, a
shorter token TTL, or forced session revocation via the admin API. This
ADR picks the version check.

**Fact checked during the 2026-09-26 revision:** the client's axios
interceptor (`client/src/lib/api.ts`) calls `supabase.auth.signOut()` on
*every* 401 — it does not refresh and retry. The original draft assumed
"a 401 forces a transparent refresh", which is not true for this client
today. The design below therefore includes the client change explicitly.

## Beslissing

**Principle: Postgres is the source of truth for a user's permissions;
GoTrue `app_metadata` is a cache of it.** Every design choice below
follows from that — a cache may be briefly wrong, but it must always be
repairable from the source, and repair must never depend on the failed
write being retried by whoever caused it.

1. **Schema.** `profiles.permission_version integer not null default 1`.

2. **Every write path: DB first, then push the cache, reading version
   and permissions together.**
   - The bump is one atomic statement, `UPDATE profiles SET
     permission_version = permission_version + 1 WHERE ... RETURNING id,
     permission_version` — for `PATCH /:id/role` (one row) and for
     `roles.ts`'s holder loop (all rows with that `role_id`).
   - The `app_metadata` push is built by a single helper,
     `buildAppMetadata(profileId)`, which reads `tenant_id`, `role_id`,
     `roles.permissions`, and `permission_version` **in one query** at
     push time. A version number therefore always travels with the
     permission set it belongs to — never a new number with an old
     permission set.
   - If the push fails, the request still succeeds (the DB change is
     real and already enforced); the cache is repaired lazily by step 4.
     No compensating DB rollback, no retry queue.

3. **All four call sites use the helper** — `provision_tenant` (first
   admin, version 1), `POST /invite` (every invited user, version 1),
   `PATCH /:id/role`, and `roles.ts`'s holder loop. The invite path is
   load-bearing: a token that never had the claim can't be fixed by a
   refresh alone.

4. **`requireAuth` check and self-repair.** After validating the token,
   one query reads `profiles.permission_version` and `is_active`:
   - Claim equals DB value (compared as numbers) → continue.
   - Claim missing, non-numeric, or different → **re-push the cache from
     the DB** with `buildAppMetadata()` (admin client — this is user
     management, allowed by Rule 1), then respond
     `401 { code: 'token_stale' }`. The client's next refresh picks up
     the now-correct `app_metadata`. Because the repair happens here, a
     failed or out-of-order push in step 2 heals on the user's very next
     request instead of looping.
   - Profile row missing or `is_active = false` →
     `401 { code: 'account_inactive' }`. No repair, no refresh.

5. **Client handling (`client/src/lib/api.ts`).**
   - `token_stale` → `supabase.auth.refreshSession()`, then retry the
     original request **once**. A second `token_stale` on the retry →
     sign out (hard stop — no loop is possible by construction).
   - `account_inactive` → sign out immediately, show "your account is
     no longer active".
   - Any other 401 → sign out (current behavior).

6. **Rollout without a thundering herd.** An env flag
   `PERMISSION_VERSION_ENFORCE` (default `false`):
   - While `false`: a *missing* claim is treated as legacy — the request
     is allowed and the cache is re-pushed in the background (so the
     user's next natural refresh carries the claim). A *present but
     different* claim is still rejected, so demotions are enforced from
     day one.
   - Flip to `true` once every active token carries the claim (at the
     latest after one token TTL, ~1h; in practice wait 24h). No forced
     mass-refresh ever happens.

7. **Stated assumption.** The only API consumer is the browser SPA. A
   future mobile app or service-to-service caller must implement the
   same `token_stale` / `account_inactive` handling, or revisit this ADR.

## Redenen

- **Cache + self-repair instead of a distributed transaction.** Postgres
  and GoTrue can't share a transaction. Every fixed ordering (DB first or
  GoTrue first) leaves a window where one write succeeded and the other
  didn't — the original draft's infinite-401 scenario. Making the DB
  authoritative and letting `requireAuth` rebuild the cache from it
  removes the need for the two writes to succeed together at all.
- **Version and permissions read in one query** is what closes the
  last-write-wins race between concurrent role changes: an out-of-order
  push can only ever install an *older consistent pair*, which the
  version check then detects and repairs.
- **Distinct error codes** let the client tell "refresh fixes this"
  apart from "log out, nothing will fix this", and the single-retry rule
  makes a refresh loop structurally impossible even if the server
  misbehaves.
- **Enforcement flag** turns deploy day from "every active session gets a
  401 at once" into a no-op.
- Chosen over a shorter TTL (only shrinks the window) and forced session
  revocation (extra external call per change, and still leaves the same
  two-system consistency problem).

## Consequenties

- `requireAuth` goes from zero to one DB query per request (primary-key
  lookup on `profiles`). **Must be measured, not assumed:** record
  `requireAuth` latency on the staging deploy (`STORY-029`) before and
  after; target is less than 10 ms added at p95. If it's worse, revisit
  (e.g. short in-isolate caching) before enabling enforcement.
- The repair path uses the admin client inside `requireAuth` — only on a
  mismatch, never on the happy path. Rate is bounded by how often
  permissions change.
- Changes: one migration; `buildAppMetadata()` helper; four call sites;
  `requireAuth`; `client/src/lib/api.ts`; `packages/shared` auth types
  gain `permission_version`; integration tests for: invite → first
  request succeeds, demotion → next request `token_stale` → refresh →
  new permissions, failed push → self-repair, deleted profile →
  `account_inactive`, flag off → missing claim allowed.
- Resolves `STORY-030`, which is updated to point here.
- Not MVP — deferred by product decision (2026-08-01). There is **no**
  live lockout today: the check doesn't exist yet, so the invite-path
  problem only appears if the check ships without step 3.

## Review 2026-08-30 — verwerking

1. **DB-bump en GoTrue-push niet atomisch** → opgelost door het
   cache-principe (Beslissing 2 + 4): een mislukte push herstelt zichzelf
   bij het volgende verzoek, geen lus.
2. **Stormloop op deploy-dag** → vlag `PERMISSION_VERSION_ENFORCE`
   (Beslissing 6).
3. **"Profiel weg" en "verouderd" in hetzelfde 401-pad** → aparte codes
   `token_stale` / `account_inactive` + client die maximaal één keer
   opnieuw probeert (Beslissing 4 + 5).
4. **Race tussen gelijktijdige wijzigingen** → versie en rechten altijd
   samen gelezen; een verouderde push wordt gedetecteerd en hersteld
   (Beslissing 2).
5. **"Niet MVP" versus "permanente lockout"** → rechtgezet: de lockout
   bestaat vandaag niet, alleen als de check zonder invite-fix zou
   uitkomen; de invite-fix is daarom verplicht deel van dezelfde wijziging
   (Beslissing 3). p99-zorg → meten in staging met een concreet doel
   (Consequenties).
