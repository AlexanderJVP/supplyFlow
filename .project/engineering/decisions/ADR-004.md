## In gewone taal

Bij elke nieuwe klant richt jij zelf het systeem in: je bekijkt hoe ze
werken en maakt de rollen, gebruikers en goedkeuringsketens. Daarvoor heb
je toegang tot hun omgeving nodig. Dit voorstel kiest voor een apart
"support"-account per klant dat de klant altijd ziet in zijn
gebruikerslijst, dat hij zelf kan uitschakelen, en waarvan elke actie op
jouw naam gelogd wordt. Zo blijft het eerlijk en controleerbaar, wat
belangrijk is als je dit later als SaaS verkoopt.

## Context

Product decision (2026-09-26): onboarding is a service the platform owner
delivers. Roles differ per company and can't be known in advance, so the
owner studies how each customer works and then creates fitting roles,
access, approval chains (`STORY-058`) and initial data inside that
customer's tenant.

Today the only way in is `POST /api/admin/tenants`
(`X-Admin-Secret`), which creates the tenant plus **one** first admin
user. There is no concept of a platform-owner account inside a tenant.

Schema fact that constrains the options: `profiles.id` is the primary key
*and* references `auth.users(id)`, and a profile has exactly one
`tenant_id`. **One login belongs to exactly one tenant.** A single owner
login that can switch between customers is not possible without changing
that model.

Options considered:

- **(a) Owner is the first admin, hands over later.** Provision the
  tenant with the owner's address, set everything up, then invite the
  customer's admin and (maybe) leave.
- **(b) Separate, visible support account per tenant.** Next to the
  customer's own first admin, provisioning creates a dedicated support
  profile for the owner, clearly marked as such.
- **(c) Impersonation ("log in as" a customer user)** via a service-role
  flow that mints a session for someone else.

## Beslissing

Option **(b)**.

- `profiles` gains `is_platform_support boolean not null default false`.
- `POST /api/admin/tenants` accepts an optional support e-mail (the
  owner's per-customer address, e.g. a plus-address). If given, the same
  `provision_tenant` transaction creates that support profile with the
  Admin role, next to the customer's own first admin. A separate admin
  endpoint (same `X-Admin-Secret` + rate limit) can add a support account
  to an existing tenant later.
- The Admin user list shows support accounts with a clear
  "Platform support" badge. The customer's admin can deactivate or
  remove it at any time, like any other user — and can re-request it.
- Everything the support account does is attributed to that profile by
  the existing audit trigger (`log_audit_event`), the stock ledger and
  proposal reviews — no special logging path.
- Support accounts are excluded from "active users" counts and from
  approval-chain e-mails (`STORY-060`) unless explicitly placed in a
  chain.

## Redenen

- **Transparency is the product's trust story.** A SaaS customer must be
  able to see who can access their data. (b) makes the owner's access
  visible and revocable by the customer; (a) hides it behind "the admin"
  and (c) hides it entirely.
- **Correct attribution for free.** Every action already records the
  acting profile. In (b) that profile *is* the owner's support account,
  so audit logs say exactly who did what. In (c), actions would be logged
  under the impersonated customer user — the audit trail would lie.
- **Fits the schema as-is.** (b) is one boolean column plus a provisioning
  option; no change to the one-login-one-tenant model, no new
  authentication flow. (c) would need custom session minting with the
  service key — a new, sensitive code path Non-Negotiable Rule 1 tries to
  keep small.
- **(a) doesn't survive the handover cleanly:** either the owner keeps a
  full admin login nobody notices, or loses access and has to be
  re-invited for every support question.

## Consequenties

- One migration (`is_platform_support`), a provisioning option, an
  "add support account" admin endpoint, and a badge + filter in the Admin
  user list. Tracked in `EPIC-012-onboarding`.
- The owner manages one login per customer. Acceptable at the expected
  number of customers; if it becomes painful, a later ADR can revisit
  multi-tenant logins (a much larger change to `profiles`/RLS).
- Deactivating a support account depends on user deactivation existing
  (`profiles.is_active` is there, but no API/UI uses it yet) — the
  onboarding epic must include it, and `ADR-003`'s `account_inactive`
  handling makes deactivation take effect on the next request.
- Needs a line in the future terms of service / privacy statement that
  the provider may hold a visible support account during onboarding.
