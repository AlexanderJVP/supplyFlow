## Context

The product needs several capabilities that don't fit cleanly into a
single stateless request/response cycle: stock reservations (locking a
quantity of an item against concurrent claims by multiple production
orders), long-running CSV import jobs, PDF generation, and label
printing. Cloudflare Workers are stateless and short-lived, so all of
these need some form of queueing, background processing, or
coordination that a plain Worker request handler can't provide alone.

Two options were raised and rejected during discussion:

- **RabbitMQ** (self-hosted message broker) for the async/background work.
- **Durable Objects** for stock reservation locking.

Both were weighed against Cloudflare's own native primitives (Queues,
Workflows) and against the project's existing convention of using
Postgres RPCs for every multi-step/atomic mutation (see Non-Negotiable
Security Rule 4 and `engineering/architecture.md`).

## Beslissing

- **CSV import, PDF generation, and label printing** are handled by a
  single shared pattern: one Cloudflare Queue + one generic consumer
  Worker that dispatches on a `job.type` field, backed by a Postgres
  `jobs` table (`id`, `tenant_id`, `type`, `status`, `result_url`,
  `error`, `created_by`) for status tracking, with output files written
  to Cloudflare R2. The client polls `GET /jobs/:id` for status — one
  consistent pattern reused across all three job types instead of three
  separate ad-hoc implementations.
- **Stock reservations** stay in Postgres: a `reserve_stock` /
  `release_reservation` RPC pair using row-level locking
  (`SELECT ... FOR UPDATE`), following the exact same pattern already
  used by `complete_production_order`.
  - **Amended 2026-09-26 (per `ADR-002`'s review):** copying
    `complete_production_order`'s `FOR UPDATE` as-is is *not* sufficient —
    it only locks the order row, not the component stock, which is a
    derived `SUM` over `stock_ledger`. Reservations must take the same
    explicit `pg_advisory_xact_lock` guard `ADR-002` specifies for
    `move_stock` (key hashed from `(tenant_id, item_id[, location_id])`,
    acquired in sorted key order). See `STORY-035` and `STORY-043`.
- **RabbitMQ is explicitly rejected** as a dependency for this project.
- **Durable Objects are explicitly rejected** for stock reservations at
  current scale.
- **Cloudflare Workflows is deferred, not rejected**: if CSV import later
  needs a multi-step human-in-the-loop flow (e.g. preview → confirm →
  commit), that specific job type can be moved from the generic Queue
  consumer to a Workflow using `waitForEvent()` — this ADR doesn't rule
  that out, it just doesn't build it preemptively.

## Redenen

- **Workers can't reasonably host a persistent RabbitMQ consumer.**
  Workers are stateless and short-lived per request; a real AMQP consumer
  expects a long-lived, continuously-listening channel. Workers do
  support raw TCP sockets (`cloudflare:sockets`), but there's no
  maintained AMQP client for the Workers runtime, so this would mean
  hand-rolling the protocol against a runtime it isn't designed for.
- **RabbitMQ means operating a broker.** It would introduce a whole new
  piece of infrastructure to host, patch, scale, and monitor — directly
  contradicting the reasoning already recorded for choosing Cloudflare
  Workers in the Tech Stack table ("Edge, fast cold start" — i.e.
  deliberately avoiding self-managed infrastructure).
- **Cloudflare Queues already covers the actual need**: at-least-once
  delivery, batching, retries, and a Dead Letter Queue, natively
  integrated with the same Wrangler/Workers deployment pipeline already
  in use — no new tooling, no new secrets, no new failure domain.
- **Stock reservations are a concurrency problem, not a queueing
  problem.** The project already has a proven, tested mechanism for
  exactly this shape of problem — a single Postgres RPC doing the
  read-check-write atomically — used successfully by
  `complete_production_order` and `apply_bom_change_payload`. Introducing
  Durable Objects would mean a second, parallel state-management
  mechanism for something Postgres already handles correctly at this
  scale (SME tenants, 10–250 employees).
- **One shared job pattern instead of three bespoke ones** keeps the
  surface area small: one queue, one consumer dispatch function, one
  status table, one client-side polling pattern — easier to secure
  (RLS/tenant-scoped like everything else) and easier to reason about
  than three independent async pipelines.

## Consequenties

- A new Cloudflare Queue and a `jobs` table/migration need to be added;
  none of this exists yet (this ADR is proposed ahead of any
  implementation — see the accompanying epic/stories, not built as part
  of this decision).
- The generic consumer Worker's dispatch function becomes the one place
  job-type-specific logic lives. Fine while there are only three job
  types; if the number of distinct job types grows substantially, revisit
  splitting into per-type consumers/queues.
- `reserve_stock`/`release_reservation` need a reservation concept added
  to the schema (likely a `stock_reservations` table or a reserved-quantity
  column derived similarly to `current_stock`) — not yet designed in
  detail; that's follow-up work, not decided here.
- If a job type later needs multi-step durability with human approval in
  the middle, it can move to Cloudflare Workflows without contradicting
  this ADR — that's an explicit deferral, not a closed door.
- No new operational dependency (broker, cluster, ops runbook) is added
  to the project beyond what Cloudflare/Supabase already require.
- This is explicitly **not MVP** — deferred to a later sprint per product
  decision (2026-08-01); the accompanying epic/stories are staged as
  `backlog`, not scheduled into current work.
